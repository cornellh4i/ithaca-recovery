# Meeting Lifecycle Flows

What each lifecycle operation writes to the database, what it syncs externally, and what the client does afterward. Read this before touching any of the routes below — the seams between operations (exclusions, trims, splits, suspensions, soft-delete) are where regressions hide. For *why* the model looks like this, see [Technical Decisions](../02-handoff/technical-decisions.md) ("Recurring-Series Edit Scopes", "Zoom Integration", "Google Calendar Sync").

Legend: **tx** = advisory-lock-guarded `$transaction` (`util/meetings/resourceLocks.ts`); **after()** = deferred post-response sync via Next's `after()`; *cat-cal* = category (calType) calendar events (`Meeting.googleCalendarEventIds`, keyed by category); *room-cal* = the Zoom-Room calendar's join-link event (`Meeting.zoomCalendarEventId`, singular; published only when `zoomRoom` is set, i.e. Hybrid).

| Op | DB writes (synchronous) | Deferred sync | Client follow-up |
|---|---|---|---|
| **Create** — `write/meeting` | **tx**: lock room/zoomRoom/zoomHost (whole pool if auto) → conflict check → resolve host → `Meeting.create` (+ `RecurrencePattern`) | `syncNewMeeting`: Zoom create first, then cat-cals, then room-cal; one combined update writes zid/link/passcode/host + both sync statuses. Skips entirely if `status === 'Suspended'` | `pollMeetingSyncStatus` (4×1.5s), failure toast |
| **Update, scope `all`** — `update/meeting` | **tx**: lock/conflict/host-resolve → `meeting.update` + pattern upsert-or-delete. A pure Zoom Room change no longer re-resolves the host | `syncUpdatedMeeting`: rehost-in-place → teardown/recreate **only** for genuine recreate reasons (refused host move); a pure room change keeps zid/link/passcode/host and just moves the room-cal event between room calendars → `updateZoomMeeting` (union schedule across zid siblings; schedule-neutral body if siblings diverge) → `reconcileMeetingCalendars` (full `events.update`; the body serializes EXDATEs and trims — see below). Skips if suspended | polls parent mid |
| **Update, scope `this` / `thisAndFollowing`** — `handleScopedEdit` | **tx**: lock parent's + child's claims → parent pattern gets `excludedDates` push (`this`) or `endDate` trim + `numberOfOccurrences: null` (`thisAndFollowing`) → conflict-check the child candidate → `meeting.create` child (`splitFromMid` = root mid; inherits zid/link/passcode/host/zoomManaged/zoomTopic; takes the payload's room/zoomRoom). 400s: mode or host change, missing/off-pattern occurrenceDate, pattern under `this` | `syncScopedParentCalendar`: full-body rewrite of parent cat-cals **and** room-cal from the post-write pattern, then writes the parent's own `googleSyncStatus`/`googleSyncError` (suspended-skip leaves status untouched, not `'error'`); `syncSplitMeeting`: child's own cat-cals + room-cal + statuses. **No Zoom API call** — the shared-zid machinery governs later PATCHes | polls parent mid and `newMid` |
| **Delete `this` / `thisAndFollowing`** — `delete/meeting` | Pattern-only write (exclusion push, or trim + count-null). No tx/lock (single write) | `syncPartialDelete`: full-body rewrite of cat-cals + room-cal from the post-write pattern, then writes `googleSyncStatus`/`googleSyncError` on the (still-live) row (suspended-skip leaves status untouched, not `'error'`) | none; toast on HTTP 200 |
| **Delete `all` / one-off** | `meeting.update({ deletedAt })` (soft) | `syncDeleteAll`: delete cat-cal events, tear down pending resume series, delete the Zoom meeting only if `zoomManaged` and no live row shares the zid, delete room-cal event. Fire-and-log | none |
| **Suspend** | **tx** (+ retry): re-check open suspension → `status:'Suspended'` + `SuspensionPeriod.create` | `syncSuspend`: UNTIL-trim cat-cals at max(from, tomorrow) via `trimCalendarEventSeries` (suspension trims are **not** pattern state — this helper exists solely for them), or delete events for a one-off; bounded suspensions pre-create the resume series into `resumeEventIds` | none |
| **Resume (now / on date)** | **tx**: single-winner `updateMany` on the unpromoted suspension; immediate resume also flips `status:'Active'` | delete/recreate pending resume events; overwrite `googleCalendarEventIds` + status | none |
| **Retry sync** — `update/meeting/sync` | Synchronous end-to-end (no `after()`): adopts live Zoom credentials → PATCH → host reservation in its own tx → room-cal → reconcile cat-cals → status writes | n/a | fresh statuses in the response |

## Invariants worth knowing

- **`buildEventBody` is the complete serializer of a `RecurrencePattern`**: RRULE plus one `EXDATE;TZID=America/New_York` line per `excludedDates` entry, with a trimmed `endDate` overriding `COUNT`. Every Google write goes through it, so a full-body rewrite is always safe *with respect to pattern state* — and never safe for suspension trims, which live only in `SuspensionPeriod` and are enforced by the suspended-skip guards in every rewrite path.
- **Trim writes null `numberOfOccurrences`** (delete and edit paths both), so a later form resubmit can't recompute an end date past the trim.
- **Split rows share the parent's `zid`**; sibling lookups query by zid, so they join the union-schedule/schedule-neutral PATCH logic automatically. Only a whole-series delete of the last referencing row deletes the Zoom meeting.
- **`reconcilePendingResume`** runs at the top of update/delete/suspend/resume as a lazy self-heal promoting due resume-series event IDs — there is no cron.
- **Sync-status asymmetry is deliberate, but narrower than it looks**: create/update/suspend/resume/retry persist statuses and badge; a partial delete (`this`/`thisAndFollowing`) does too now — its row survives (only the pattern changed), so a failed rewrite still gets `googleSyncStatus: 'error'` and the ⚠ badge/retry prompt like any other Google write. Only a whole-series/one-off delete (`syncDeleteAll`) stays fire-and-log — the row itself is gone, so there's nothing left to badge.
- **While a meeting is suspended, every calendar rewrite is deferred** — the whole-series edit, a partial edit/delete's full-body rewrite, and Retry sync all skip Google Calendar outright (see the "Skips if suspended"/"suspended-skip" notes above). Google Calendar intentionally stays stale (still showing `syncSuspend`'s UNTIL-trimmed or deleted events) for the whole suspension window; only Resume recreates events from the full current pattern.
